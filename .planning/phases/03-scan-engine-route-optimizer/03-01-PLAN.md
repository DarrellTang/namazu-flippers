<threat_model>
T-03-01: Malformed or partial API rows could enter the route and create bad player instructions. Mitigation: filter rows with non-positive item IDs/prices/profit, blank names, or blank purchase source before ranking.

T-03-02: API errors or unexpected response shape could surface as raw exceptions or nulls to Phase 4. Mitigation: return structured `ScanEngineResult` statuses and preserve technical details separately for logs.

T-03-03: Assuming remote response order could silently degrade route quality if Saddlebag changes ordering. Mitigation: always sort locally by the configured deterministic comparator.
</threat_model>

<decision_coverage>
- D-11: The plan requires verifying the Saddlebag response boundary and not relying on response order.
- D-12: `ScanEngine` ranks locally and deterministically after filtering invalid rows.
- D-13: The primary sort is `ExpectedDailyProfit` descending.
- D-14: Tie-breaks are `SalesPerDay` descending, then `CheapestPrice` ascending.
- D-15: `OutOfStock` is preserved as metadata and does not override profit or velocity ranking.
- D-16: Route willingness is protected by using configured session caps instead of theoretical max profit.
- D-17: Final stop-first selection is completed in 03-02 so `MaxServersToVisit` prevents too many low-value stops.
- D-18: Profitable one-item server stops remain allowed in the downstream route optimizer.
- D-19: Vendor opportunities are preserved distinctly with `IsVendorSource`.
- D-20: Fewer qualifying opportunities return a smaller result; thresholds are not relaxed automatically.
- D-31: Refresh-failure stale-cache fallback is completed in 03-02 after cache exists.
- D-32: Stale cache is represented by `UsingStaleCache` in the structured status model.
- D-33: Successful scans that filter to zero usable rows return a structured `Empty` result.
- D-34: Successful-but-empty scans do not reuse previous cache; cache integration in 03-02 preserves this rule.
- D-35: The plan explicitly forbids automatic threshold relaxation.
- D-36: Failures return structured `Error` results rather than null/raw exceptions.
- D-37: User messages stay friendly while technical details stay in `TechnicalDetails` and logs.
</decision_coverage>

    Constructor signature:
    ```csharp
    public ScanEngine(SaddlebagClient client, Configuration configuration, IPluginLog log)
    ```

    Add a public fresh-scan method:
    ```csharp
    public async Task<ScanEngineResult> ScanFreshAsync(CancellationToken ct = default)
    ```

    `ScanFreshAsync` must:
    - Call `client.ScanAsync(ct)`.
    - Treat `response.Items` null or empty as an `Empty` result with user message `No opportunities matched your current settings.`
    - Filter out invalid rows:
      - `ItemId <= 0`
      - blank `Name`
      - blank `CheapestServer`
      - `HomePrice <= 0`
      - `CheapestPrice <= 0`
      - `ExpectedDailyProfit <= 0`
      - `SalesPerDay <= 0`
    - Sort valid rows by:
      1. `ExpectedDailyProfit` descending
      2. `SalesPerDay` descending
      3. `CheapestPrice` ascending
    - Take at most `Math.Max(1, configuration.MaxItemsPerSession)` opportunities.
    - Return `Success` when one or more opportunities remain.
    - Return `Empty` when filtering leaves zero opportunities; do not reuse old cache in this plan.
    - Catch `ApiException` and return `Error` with a friendly user message and technical details from the exception.
    - Catch `OperationCanceledException` only when `ct.IsCancellationRequested`; rethrow or return a cancellation-aware error consistently.
    - Log concise success/empty/error status with `/nflip:` prefix.

    Add private helper methods if useful:
    - `private static bool IsUsable(ScanItem item)`
    - `private static RankedOpportunity ToOpportunity(ScanItem item)`

    Vendor detection target: set `IsVendorSource` true when `CheapestServer` equals `Vendor` or starts with `Vendor:` using ordinal-ignore-case comparison. Preserve the original source text in `PurchaseSource`.
  </action>
