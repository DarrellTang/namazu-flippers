<objective>
Close UAT Test 3 ConfigWindow Discard gap: clicking Discard does not revert the user's
edits. Save and Cancel work; only Discard is broken. Root cause (per
`.planning/debug/discard-not-reverting.md`):

Dalamud's `WindowHost.DrawInternal` fires `OnOpen()` whenever `internalLastIsOpen`
transitions false→true. When the user closes a dirty ConfigWindow:

```
Frame N+1: DrawInternal sets internalLastIsOpen=false → calls OnClose()
           OnClose() sees isDirty=true, sets IsOpen=true to cancel close,
                     sets showUnsavedModal=true
Frame N+2: DrawInternal sees internalLastIsOpen(false) → IsOpen(true) = TRUE
           OnOpen() fires unconditionally
           snapshot = Snapshot(plugin.Configuration) — BUT Configuration already
                     holds the user's edited values, so snapshot is corrupted
User clicks Discard:
           RestoreFrom(snapshot, plugin.Configuration) — restores corrupted (edited)
                     snapshot — net effect: no revert
```

The snapshot/restore mechanics are correct. The Snapshot() and RestoreFrom() methods
deep-copy all 17 fields including arrays. The bug is purely WHEN the snapshot is
captured.

**Fix (one-line guard, taken verbatim from `discard-not-reverting.md` resolution):**

In `OnOpen()` at ConfigWindow.cs:45-49, wrap the snapshot capture in a `!isDirty`
guard. A genuine new open always has `isDirty == false` (Save and Discard both clear
isDirty before closing; Cancel keeps the window open without firing OnClose). The
spurious bounce from OnClose has `isDirty == true`. The guard correctly distinguishes
the two paths.

The `selectedWorldIndex` re-sync from `plugin.Configuration.HomeWorld` is also moved
inside the guard — on a spurious bounce we want to preserve the user's in-progress
edits including any pending HomeWorld selection.

Purpose: Restores UI-08 D-12 contract (snapshot/dirty/save/discard flow). After this
plan, the Discard button correctly reverts all 14+ Configuration properties to their
pre-edit state, matching the working Save and Cancel paths.

Output: 1 file modified (ConfigWindow.cs); 1 test file extended (phase04_nyquist.sh);
UAT Test 3 Discard gap closes at the source level.
</objective>

Current code:
```csharp
public override void OnOpen()
{
    snapshot = Snapshot(plugin.Configuration);
    isDirty = false;
    selectedWorldIndex = Array.IndexOf(WorldData.KnownWorlds, plugin.Configuration.HomeWorld);
}
```

Replacement code:
```csharp
public override void OnOpen()
{
    // Guard against Dalamud's WindowHost.DrawInternal spuriously firing OnOpen on the
    // frame after OnClose cancels a dirty close (sets IsOpen = true to keep the window
    // alive while the unsaved-changes modal renders). On a genuine new open, isDirty
    // is always false because Save and Discard both clear it before closing, and
    // Cancel keeps the window open without dispatching OnClose. On the spurious
    // re-open, isDirty is true — and re-snapshotting at that moment would capture
    // the user's edited values, corrupting the Discard restore path.
    if (!isDirty)
    {
        snapshot = Snapshot(plugin.Configuration);
        selectedWorldIndex = Array.IndexOf(WorldData.KnownWorlds, plugin.Configuration.HomeWorld);
    }
}
```

**Why `isDirty = false` is removed from inside the body:** Previously the unguarded
OnOpen always reset isDirty to false. With the guard, that line is unreachable when
isDirty is true (no-op anyway) and redundant when isDirty is false (constructor
default + always cleared by Save/Discard before close). Removing the `isDirty = false`
line ensures the spurious-bounce path doesn't accidentally clear the dirty flag and
hide unsaved changes from the modal trigger logic.

**Why selectedWorldIndex moves inside the guard:** Same reason. On a genuine open,
we want the dropdown selection to match the persisted HomeWorld. On a spurious bounce
during dirty editing, we want whatever in-progress dropdown selection the user had
preserved — re-syncing from plugin.Configuration.HomeWorld would discard a pending
HomeWorld change the user hasn't yet Saved or Discarded.

**No other changes to ConfigWindow.cs.** The OnClose handler (lines 52-59), the Draw
method (lines 61-315), the Snapshot/RestoreFrom helpers (lines 334-377), and
RestoreDefaults (lines 379-398) are untouched.

**No data-model changes.** No changes to NamazuFlippers.cs, DailyRouteWindow.cs,
Configuration.cs, FirstRunWindow.cs, or any Phase 3 file.

**Why this fix is sufficient (verifying coverage of all three modal-resolve paths):**
- **Save path:** clears isDirty (line 258), sets IsOpen=false (line 296). On the
  next genuine open, isDirty is false → guard allows snapshot. Correct.
- **Discard path:** restores Configuration from snapshot (line 302), clears isDirty

- **Spurious bounce after OnClose cancellation:** OnOpen fires with isDirty=true →

  Discard now restores correctly. Fixed.

**Why both assertions matter:**
- The `if (!isDirty)` check guards against future refactors that might remove the
  guard "to simplify" the code, re-introducing the bug.
- The `snapshot = Snapshot(...)` call is what the guard protects. Asserting it
  remains in the file ensures a refactor doesn't accidentally delete the snapshot
  logic entirely while preserving the guard.

The pair together pins the fix shape: a guard wrapping a snapshot capture.

**Why grep-comment-hygiene applies (and is fine):** ConfigWindow.cs uses `//` line
comments. The replacement code in Task 1 includes a multi-line comment explaining
the Dalamud WindowHost behavior. The `if (!isDirty)` and `snapshot = Snapshot(...)`
patterns will appear in code, not in comments. Grep-without-comment-strip is
acceptable here because:
  1. We use `require_pattern` (presence, not count) — even if the pattern appeared
     in a comment, it would still be a fingerprint of the fix.
  2. The risk pattern is the OPPOSITE: the guard being removed. A removal would
     drop both the code line and any comment referencing it; the assertion fails
     either way.

**Note on absent_pattern alternative:** We do NOT add an absent-pattern check for
the unguarded `snapshot = Snapshot` line, because the guarded version contains the
same string. An absent-pattern check would mis-fire. The presence-pattern pair
above is the right shape.
