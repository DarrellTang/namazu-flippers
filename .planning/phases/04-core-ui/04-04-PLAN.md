<objective>
Close UAT Test 1 gap: profit tally permanently displays zero because the listed-checkbox
column is never rendered. Root cause (per `.planning/debug/profit-tally-shows-zero.md`):
`DailyRouteWindow.DrawRouteStop` lines 196-198 compute `isHomeStop = stop.PurchaseSource
.Equals(plugin.Configuration.HomeWorld)` and only call `DrawItems(stop, isHomeStop:true)`
in that case. But `RouteStop.PurchaseSource` is set in `RouteOptimizer.CreateRouteStop`
to the cheap purchase server (away server) — never to `HomeWorld`. The home world is
only used to compute `TravelFriction`. There is no `RouteStop` in the route whose
`PurchaseSource` matches the home world, so `isHomeStop` is structurally always false,
`##listed-{itemId}` is never drawn, `listedState` stays empty, and the profit tally
(which sums `ExpectedDailyProfit` over listed items) is always zero.

**Design decision — render listed inline on every item row, do NOT synthesize a home stop:**

The orchestrator's gap entry presents two options:
  (a) synthesize a home/listing stop in RouteOptimizer (modifies Phase 3 source files),
  (b) render the listed-checkbox column inline on every item row everywhere (UI-only).

This plan picks **option (b)** for the following reasons:
  1. **Listed state is per-item, not per-stop.** A player lists every flipped item on
     the home market board after buying it from wherever it was cheap. The listing
     action is independent of where the item was purchased — there is no semantic
     reason to gate "listed" on a stop being "home".
  2. **No Phase 3 churn.** Option (a) would require modifying `RouteStop.cs` (add
     `IsHomeStop` flag) AND `RouteOptimizer.cs` (set it OR synthesize a synthetic
     home-listing stop). Both files are Phase 3 deliverables; their nyquist gate
     (`tests/phase03_nyquist.sh`) is the canonical contract for that phase. Option
     (b) keeps the fix entirely inside Phase 4's scope.
  3. **Better UX.** Listing inline on each row means the user can mark "listed"
     immediately when they see the buy/profit data — no scroll-to-bottom required.
  4. **Matches actual data flow.** The user's FFXIV workflow is: buy at cheap server,
     teleport home, list everything. The plugin already shows all items grouped by
     buy server. Adding a listed-checkbox to every row mirrors the actual workflow:
     "buy this item (bought-checkbox), and when you get home, list it (listed-checkbox)."

Layout per row becomes:
  `[bought] ItemName  [Vendor] [OOS]  Buy: X,XXX  +X,XXX/day  [listed]  List: X,XXX`

Purpose: Restores UI-04 (profit tally that updates with listed checkboxes) and refines
UI-03 (listed checkbox semantics — now per-item, not "home stop only" since no home
stop ever exists). UI-SPEC's "Listed checkbox: in home stop section only" line is
adjusted in spirit because the home stop section is unreachable; the listed control
remains, just rendered inline.

Output: 1 file modified (DailyRouteWindow.cs); 1 test file extended (phase04_nyquist.sh);
profit tally works end-to-end after the user marks items listed.
</objective>
